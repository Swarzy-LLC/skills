# Test audit

- Every new or changed test passes the authoring gate below.
- An audit removes low-value proof in coherent batches grouped by production owner. Never chase deletion counts.
- For a whole-subsystem pruning campaign, read [CAMPAIGN.md](CAMPAIGN.md) first.

## Discover the repo first

Learn how this repo tests before you judge or write anything. Hardcode nothing.

1. Read the repo's agent instructions: root and scoped `AGENTS.md` (or `CLAUDE.md`), and `.agents/test-audit.md` if present. Local rules there override this skill. See [Per-repo overrides](#per-repo-overrides).
2. Find the test runners and their configs: `vitest.config.*`, `bunfig.toml` or `bun test` scripts, `playwright.config.*`, `test/` or `spec/` with `test_helper.rb`, `jest.config.*`, `pytest.ini` or `pyproject.toml`, `go.mod`, and so on.
3. Find the repo's own commands, in this order:
   - `hk.pkl` hooks and steps (`hk check`, `hk fix`);
   - `mise tasks ls` and `[tasks]` in `mise.toml`;
   - `package.json` scripts;
   - `Rakefile`, `bin/rails`, `bin/*`, `Makefile`, `justfile`;
   - CI workflows, which show what actually gates a merge.
4. Use [references/stacks.md](references/stacks.md) for focused-run syntax, common test-only seams, and dead-code tools per stack.

If the repo uses mise, run tools through it (`mise exec --` or `mise run`) so you get its pinned versions.

## Authoring gate

Before adding or changing a test, answer all four questions:

1. What observable behavior, invariant, or independent contract does it protect?
2. What credible regression would make it fail?
3. Why does existing proof miss that regression? Each contract has one primary owner test at the strongest boundary that can see it. A second layer needs a distinct risk, such as a different transport or lifecycle. Prefer adding a row to an existing table test or shared fixture over a new test, and consolidate repeated setup.
4. Does it need an export, flag, wrapper, or injection hook that no production code uses? If so, move the proof to the real boundary instead.

Also:

- A regression test must fail before the fix for the intended reason and pass after it. If you cannot show the failing baseline, say so in your report.
- One regression test at the owning layer covers a bug. Do not replay it at every layer the bug crossed.
- A behavior-preserving refactor should not break the test. If it would, the test is coupled to the implementation.
- Prefer table-driven or parametrized tests for variations of one contract.

## Junk patterns

Reject these in new tests, and flag them when auditing existing ones:

- Self-comparisons, copied inventories, source greps, and assertions on implementation details or call shapes.
- Duplicate proof of a contract already owned elsewhere.
- Test-only seams in production code.
- Expected values generated by the code under test.
- Mocks that supply the behavior being asserted.
- Fixtures that fabricate results, receipts, or ordering the owner is supposed to produce, or that assert persistence through a path the code never writes.
- Negative controls that pass because of an unrelated guard. A negative test must fail at the guard it names.
- Test names that promise behavior the test never exercises.

The full checklist is in [references/audit.md](references/audit.md#junk-patterns).

## Retention bar

- Keep tests that guard independent contracts: public API, SDK, protocol, config, migration, storage, security, platform, defaults, exact prompt or output bytes, generated cross-language code, packaging, release, architecture, and observable ordering. Being static or slow is not a reason to delete a test.
- A test that inspects source is valid only if it guards an independent user-facing contract and survives renaming identifiers.
- A baseline failure may be a product bug. Reproduce it and fix the owner; do not delete the test to get green.

## Audit and validation

- Before any audit edit, gather the [candidate evidence](references/audit.md#candidate-evidence): read the full test, its production owner, callers, and history, and record what proof remains before you delete anything.
- Delete obsolete production seams together with their tests. Never optimize for deletion counts.
- Never skip, disable, or delete a test just to make a run pass.
- Validate with the repo's own commands from discovery. When the repo has mise or hk, run through them, for example `hk check` plus the focused tests for each touched owner and its siblings.
- Browser tests use Playwright or agent-browser, not Selenium.
- Keep comments in tests minimal: at most a line or two of context, and none on self-evident code.
- Report causes, retained contracts, proof and its cost, production versus test lines changed, and follow-ups.
- Commit, push, or merge only when the human has given you that authority for this task.

## Per-repo overrides

A repo can tune this skill without forking it. Put local rules in a `Testing` section of `AGENTS.md`, or in `.agents/test-audit.md`. Useful entries:

- the exact commands for focused, full, and browser test runs;
- boundaries: suites or directories that are off limits, or that must never be deleted;
- the preferred keeper boundary per subsystem, such as "HTTP fixture suites own API contracts";
- extra contracts to retain, and known flaky tests with their tracking issue;
- line-count or coverage baselines that may only shrink.

Where an override conflicts with this skill, follow the override and mention it in your report.
